# 作業規律（全モデル・全セッション共通）

高性能モデルが暗黙にやっていた判断を明文化したもの。手順として必ず実行する。

## 着手前チェックリスト（コード変更を伴う作業すべて）

1. **実コードで現状を検証する** — Issue やメモリの記述を鵜呑みにせず、Read/grep で実装状況を確認してから着手する（2026-06 棚卸しで「未着手」Issue 10 件が実装済みの閉じ忘れだった）
2. **GitHub Issue を先に立てる** — ブランチ名・コミットに Issue 番号を含める
3. **`git checkout -b feature/<issue>-<slug>` を切ってから書く** — develop 直コミットしてしまったら `git branch <feat>` で退避 → `git reset --hard origin/develop` → feature を push でリカバリ
4. **同一リポで並行セッションを走らせない** — git 状態を奪い合い stash 破壊の実害あり。衝突したら作業物を /tmp に退避して待つ

## 完了条件（Definition of Done）

- **build / テスト通過を PR の必須条件にする**。build 未確認のマージは過去に本番を破壊している
- 変更が API に及ぶなら `pnpm run openapi:export`（Server）→ App 側 `npm run sync:openapi` + `gen:api-types` で型ドリフトを防ぐ
- 実装完了時に Issue へ要約コメント、push 後にコミットリンクを追記

## 障害対応の規律

- **不完全な計測値でパニック修正しない** — X imp 低下等は計測が揃うまで待つ。A/B 判定は最低 3 日確保
- **対症療法ループに入らない** — 同じ系統のエラーで 2 回対処して直らなければ、手を止めて先行事例（動いている類似プロジェクトの設定ファイル）を読む。実例: iOS 配信は xcodebuild 直叩きで 7 ビルド失敗 → 最初から fastlane（FortuneTellingApp の Fastfile がリファレンス）
- TestFlight upload 前に `xcrun altool --validate-app` を必ず通す（Info.plist 不整合を投げる前に検出）
- パターンマッチで「知っている障害」と即断しない。システム状態を変える操作（再起動・削除・設定変更）の前に、証拠がその操作を支持しているか確認する

## 推測の禁止

- ファイル・関数・API の存在や挙動を**推測で語らない**。必ず Read/grep/実行で確認してから述べる
- メモリ（`MEMORY.md` 配下）は過去時点の観測。file:line やフラグ名は現行コードで再確認してから使う
- 不確実な設計判断は選択肢と推奨を添えてユーザーに確認する。破壊的操作・外向き操作（投稿・課金・削除）は承認が先

## プロダクト品質の判断軸

- 鑑定不能ゼロ原則: 列挙可能な空間（命数 1-60 / 12 タイプ / 366 日等）は 100% 埋める。「データがありません」を返さない
- 暦の境界（旧暦元日 / 立春 / 24 節気 / 閏年 / 月末）は必ずテストで担保する
- 「凶」を煽らない。避け方・対処法・補完手段を必ず併記する
